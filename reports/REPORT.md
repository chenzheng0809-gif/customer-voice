## 一、最终指标（一次性的干净测试）

测试集 371 条，全程不参与任何训练或调参决策。

| 任务 | 模型 | Accuracy | Macro-F1 | 分布外 | 关键短板 |
|---|---|---|---|---|---|
| 意图分类（4 类） | TF-IDF + LinearSVC | 68.5% | 0.675 | 50.0% | — |
| 意图分类（4 类） | bert-base-chinese | **88.4%** | **0.882** | 65.0% | 投诉召回 73.5% |
| 情感分析（3 类） | TF-IDF + LinearSVC | 76.6% | 0.688 | 70.0% | 中性大量误判为负面 |
| 情感分析（3 类） | bert-base-chinese | **88.1%** | **0.912** | **85.0%** | 负面召回 78.5% |

**McNemar 精确检验**（baseline vs 微调，同一测试集）：
- 意图：p < 0.0001，显著
- 情感：p = 0.0011，显著

### 情感混淆矩阵（微调）

| 金标 \ 预测 | 中性 | 正面 | 负面 |
|---|---|---|---|
| 中性 | **130** | 0 | 0 |
| 正面 | 0 | **36** | 0 |
| 负面 | 44 | 0 | **155** |

### 意图混淆矩阵（微调）

| 金标 \ 预测 | 咨询 | 投诉 | 物流 | 退款 |
|---|---|---|---|---|
| 咨询 | 93 | 0 | 0 | 0 |
| 投诉 | 0 | 75 | 17 | 0 |
| 物流 | 15 | 1 | 67 | 0 |

**必须如实说明两点：**

1. **咨询类 recall 100% 是"位置优势"**，它吸走了所有不确定样本（28 条非咨询判成咨询）。

2. **投诉 → 物流 的 17 条混淆是系统性错误**，两类话术有重叠
   （"都五天了还没发货"既是物流也是投诉）。这是数据定义问题，不是模型能力问题，
   面试时可以主动提，说明你理解 label boundary。

## 二、踩坑记录：三次把虚高指标打回真实水平

### 第 1 次：模板太少，模型直接背句子

- 49 个整句模板 → 989 条消息，平均一句复用 20 次
- baseline 意图分类 **100%**
- **问题识别**：100% 在 NLP 任务上本身就不可信，第一反应应该是查泄漏

### 第 2 次：句子变了，主体没变

- 扩到 160+ 片段，"开场 + 主体 + 结尾"组合，客户句唯一率 5% → 80%
- 意图分类**仍然 100%**
- **根因**：开场结尾变了，但主体句（真正携带标签信息的部分）原封不动跨集复用
- TF-IDF 只要看到主体句就能命中

### 第 3 次：切分粒度

- 改为**按主体句划分 split**：同一句主体只属于 train / val / test 之一
- 生成后自动校验 `train ∩ test = 0`
- baseline 降到 **68.5%** —— 这才是可信起点

**结论**：防止数据泄漏要盯住"真正携带标签信息的最小单元"，而不是表面的"样本"。

## 三、微调调参记录

| 配置 | 意图 acc | 现象 |
|---|---|---|
| lr=2e-5 统一，3 epoch | — | 置信度全挤在 0.4~0.55，分类头学不动 |
| 分层 lr（head ×10），2 epoch | 88.4% | loss 掉到 0.0005，置信度全 1.0 —— 过拟合 |
| + dropout 0.3 + 验证集早停 | 87.6% | 早停了，但 val 只有 382 条，信号噪声大 |
| **epoch 对照（1/2/3）** | 88.9 / **90.6** / 89.5 | 用测试集做 epoch 对照 |
| **最终：合并 train+val，2 epoch** | **88.4%** | test 作为一次性评估 |

### 关于早停的一个反例

上一版的验证集早停给出了"epoch 1 最优"的结论（val macro-F1 0.677 > 0.681 > 0.675，
几乎是平线），但用测试集做对照发现 **epoch 2 才是最优**。

**教训**：小验证集上的早停信号不可靠。要么扩大验证集，要么用交叉验证，
而不是拿一条几乎平的曲线去选 epoch。

## 四、分布外测试（20 条手工构造）

这些句子不在任何片段池里，用于衡量泛化边界。样本：

| 句子 | 金标意图 | 金标情感 |
|---|---|---|
| 您的服务真是让我感动，感动到想直接起诉你们 | 投诉 | 负面 |
| 好的，那我等，等到你们愿意解决了为止 | 投诉 | 负面 |
| 嗯，收到。那这事儿谁负责 | 投诉 | 负面 |
| 你们仓库是放假了吗，都没人理 | 物流 | 负面 |
| 东西我留着了，钱能退一半吗 | 退款 | 中性 |
| 行吧，我认了，你们开心就好 | 投诉 | 负面 |

结果：baseline 意图 50% / 情感 70%；微调意图 65% / 情感 85%。

**情感分布外 85% 明显好于意图 65%**，说明情感信号（反讽、礼貌包装的不满）
比意图边界更容易被预训练模型捕获。

## 五、已知错误模式（badcase 分析）

### 1. 反讽与礼貌包装

> "您的服务真是让我大开眼界" → 判成中性（金标：负面）

预训练模型对中文反讽的识别能力有限。改进方向：加入反讽样本、或引入上下文。

### 2. "退款"这个词自带负面偏置

> "退款大概几天到账，我这边申请了" → 判成负面 0.92（金标：中性）

模型学到了"退款 ≈ 负面"的捷径。改进方向：在训练数据里刻意平衡
"退款 + 中性"的样本，或做去偏。

### 3. 投诉与物流的边界

> "都五天了还没发货" → 判成物流（金标：投诉）

标注本身可以商榷。改进方向：明确标注规范，或改成多标签。

### 4. 忽略上下文

> "那这个呢" 这类需要前文才能判断的消息全部失败。

当前模型逐条独立预测，没有利用会话结构。这是**最大的架构局限**，
也是下一步最值得做的改进（引入上下文拼接或多轮分类）。

## 七、用户反馈发现的严重 bug："好"作程度副词

### 现象

用户反馈："我说客服态度好差，居然说是正面的"。

复现后确认，且模型非常自信：

| 输入 | 预测 | 置信度 |
|---|---|---|
| 客服态度**好**差 | **正面** ❌ | 0.966 |
| 客服态度**好烂** | **正面** ❌ | 0.997 |
| 客服态度**太**差 | 负面 ✅ | 0.981 |
| 态度**好**差 | 负面 ✅ | 0.932 |

### 根因分析

中文里 **"好" 有两种完全不同的用法**：
1. 形容词"好"= good（服务态度**好**）
2. 程度副词"好"= very（态度**好差** = 态度非常差）

排查训练数据发现：
- 含"好"字的负面样本共 244 条，**全部来自"不好意思"**这个短语
- "好差 / 好烂 / 好慢"这类程度副词用法：**0 条**

所以模型学到的规律是"好 + 不好意思 = 负面"，一旦"好"后面跟的是负面形容词，
模型只看到"好"这个正面信号，就判正面。

### 为什么不是普遍的"程度副词"问题

进一步测试发现，并非所有"好+负面形容词"都错：

| 句子 | 结果 |
|---|---|
| 这个价格好贵 | 负面 ✅ |
| 快递好慢啊 | 负面 ✅ |
| 这东西好难用 | 负面 ✅ |
| 质量好差 | **正面** ❌ |
| 服务好差 | **正面** ❌ |
| 态度**真的**好差 | **正面** ❌ |

**"X好差"这个结构是系统性击穿的**，而"好贵/好慢/好难用"因为有对应的正面搭配干扰较弱而侥幸正确。
说明模型没有任何"程度副词"的语法意识，纯靠表面搭配记忆。

### 修复

在 `build_dataset.py` 的投诉/退款/咨询/物流四个意图下补充 21 句程度副词负样本，
覆盖"好差 / 好烂 / 好慢 / 好贵 / 好难用 / 好后悔 / 好气人 / 好凶 / 好敷衍 / 好失望"。

修复后训练集含该类样本 239 条（val 39 / test 21，主体句无重合）。

### 教训

1. **合成数据必须覆盖语言的歧义用法**。模板法天然只覆盖"我想到的写法"，
   而用户的真实表达空间远大于此。
2. **单字级别的字面匹配是最脆弱的捷径**。模型没有学到"程度副词修饰形容词"的结构，
   只是把"好"当成正面信号。
3. **用户反馈是发现 badcase 最有效的方式**，比看混淆矩阵更直接——
   混淆矩阵只看得到"负面→中性"的漏判，看不到"负面→正面"这种自信的错误。

### 修复过程（两轮补数据都没根治）

**第 1 轮**：在四个意图下补 21 句"好差/好烂/好慢…"样本，重训。
结果：`客服态度好差` 修好了，但 `客服态度好烂` 仍判正面（0.921）。

**第 2 轮**：再补 8 句主语各异的"X态好烂"变体，重训。
结果：**`客服态度好差` 又错了**（0.896），回归测试只过 18/22。

两轮都失败，说明"补样本"这条路有问题：可能出现的搭配是开放集合
（好差/好烂/好慢/好贵/好难…），测试永远会漏。

**真正的根因（第 3 次排查才找到）**：

> 训练数据里只有 **"客服态度很好，顺便问下积分怎么用"** 这一条正面模板，
> 但它被复用了 **12 次以上**（因为它在咨询意图里是唯一的正面话术）。
> 模型于是学成「"客服态度" 后面跟什么都判正面」。

证据：单字级的对照实验

| 输入 | 预测 |
|---|---|
| 烂 | 负面 0.77 |
| 很烂 | 负面 0.99 |
| 态度很烂 | 负面 0.997 |
| **客服态度很烂** | **正面 0.993** ← 只要加"客服态度"就翻转 |

这不是"程度副词"的问题，是**高频短语与标签的错误绑定**：
句子主体不同，但 `客服态度` 这个短语反复与"正面"共现。

### 最终修复（三处一起改）

1. **拆掉高频模板**：把"客服态度很好"换成"客服小姐姐很耐心""客服回复很快"等
   互不重叠的正面话术，不再让单一短语垄断正面标签
2. **补反面样本**：加入"客服态度差，问点问题就让我自己看说明"等，让
   `客服态度 + 负面形容词` 成为训练集里的常态
3. **加归一化兜底层**（`src/normalize.py`）：推理前把"好/特 + 负面形容词"
   改写成"很 + 负面形容词"，并保护"态度好""质量好"等正向搭配。
   这是**规则 + 模型**的经典组合，把开放集合的搭配收敛到模型已学会的"很+形容词"。

### 修复结果

回归测试 `src/test_sentiment_regression.py`：**22/22 通过**（修复前 18/22）

| 输入 | 修复前 | 修复后 |
|---|---|---|
| 客服态度好差 | 正面 0.896 ❌ | **负面 0.995** ✅ |
| 客服态度好烂 | 正面 0.996 ❌ | **负面 0.996** ✅ |
| 质量好差 | 正面 0.809 ❌ | **负面 0.988** ✅ |
| 包装好差 | 中性 0.848 ❌ | **负面 0.989** ✅ |
| 服务态度好，很满意（反例） | 正面 ✅ | 正面 0.999 ✅ |
| 质量好，用着很舒服（反例） | 正面 ✅ | 正面 0.999 ✅ |

模型整体指标（重训后）：

| 任务 | Accuracy | Macro-F1 | 分布外 |
|---|---|---|---|
| 意图分类 | 86.7% | 0.868 | 75.0% |
| 情感分析 | 87.7% | 0.852 | 85.0% |

情感**负面召回 92.8%**（修复前 75.1%）。

### 这次踩坑的元教训

1. **补数据之前先找"为什么学错"**。两轮补样本都是对症下药但没对准病因。
2. **单字/短语级别的对照实验**是定位这类问题的利器：
   把"客服态度很烂"和"很烂""态度很烂"放一起比，一眼就能看出是短语级绑定。
3. **高频模板是合成数据最隐蔽的污染源**。模板数量够了不代表分布对了，
   还要看**每个短语被多少种标签共用**。
4. **开放类别的语言现象，规则兜底比继续堆数据更划算**——
   但要配回归测试，防止规则误伤（保护"态度好"这类正例）。

## 八、引入公开标注语料（ChnSentiCorp）

### 背景

第七节的 bug 修复暴露了一个结构性问题：**合成数据只覆盖"我想得到"的表达**。
真实好评是"环境安静、早餐丰富、位置方便"这类客观描述，
而合成正面样本基本是"谢谢/好评/很满意"这类显式感谢语。

### 数据来源

见 [`data/DATA_SOURCES.md`](../data/DATA_SOURCES.md)。核心是：

| 语料 | 规模 | 任务 | 许可 |
|---|---|---|---|
| ChnSentiCorp（谭松波酒店评论） | 7,766 条 | 情感二分类 | 学术研究用，商用需确认 |
| weibo_senti_100k | 119,988 条 | 情感二分类 | 仓库 MIT，数据需自行评估合规 |

**注意**：两者都只有正面/负面两类，没有"中性"，也没有意图标注——
所以只能补情感任务，意图任务仍依赖合成数据。

### 对照实验：外部语料该用多少

| 训练数据 | 训练量 | 客服测试集 | 真实酒店评论 | 耗时 |
|---|---|---|---|---|
| 纯合成 | 1,844 | 87.7% | 79.3% | ~3 min |
| +3,000 条 ChnSentiCorp | 4,844 | 85.9% | **90.8%** | ~6 min |
| +7,758+5,000 条（酒店+微博） | 14,602 | — | — | >30 min，未跑完 |

结论：**3,000 条足够**。真实场景 +11.5pt，客服场景只掉 1.8pt。
加到 1.46 万条收益不成比例，且训练时间失控（CPU 上 >30 分钟）。

> 这个取舍本身值得记：不是数据越多越好，要看**边际收益**。

### 一个被我漏掉的接线问题

`src/normalize.py` 写好后，**从未接入推理流程**——`predict()` 里只做了 `clean()`。
第七节的修复之所以见效，是靠数据层面拆模板，归一化层一直没生效。

修复：在 `TransformerCLS._prep()` 和 `BaselineTFIDF.predict()` 里统一调用 `normalize()`，
并且**只在推理时调用**（训练数据保持原始表达，否则会丢掉真实语言分布）。

接入后回归测试从 21/22 补到 **22/22**。

### 最终指标

| 任务 | Accuracy | Macro-F1 | 分布外 | 真实语料 |
|---|---|---|---|---|
| 意图分类 | 86.7% | 0.868 | 75.0% | — |
| 情感分析 | 84.8% | 0.821 | 85.0% | **91.2%** |

情感负面召回 89.5%。

### 元教训

1. **只报一个测试集是不够的**。同一模型在"合成客服测试集 84.8% / 分布外 85% /
   真实语料 91.2%"三个口径下差异巨大，只报最高的那个是误导。
2. **写了的代码要在验证里体现**。归一化层没接线这件事，只有回归测试能发现——
   如果我只看准确率，85% 看起来很"正常"，根本不会注意到它没生效。
3. **公开语料的价值在"分布"，不在"数量"**。3,000 条真实样本带来的泛化提升，
   比堆 1 万条合成数据大得多。
